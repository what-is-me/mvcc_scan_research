# 实验笔记 — 实证结论与分析记录

本文件是研究日志：记录定性结论、归因框架、方法论教训与未定案决策。
它**不是规范**——协议、不变式与契约的唯一权威是 AGENTS.md；两者冲突时
以 AGENTS.md 为准。本文里"待查 / 待验证"标注的条目是未闭合的问题，
不是结论。

**本文件有意不保存具体实测数字。**单一环境、单轮实验的绝对值与百分比
不可外推，留在文档里会锚定后续设计与实现的判断（快盘上的排序在慢盘上
会反转，见 §1.3 / §2 的"全驻留固定税"）。这里只沉淀方向性结论与因果
机制。原始数据随实验产生：本地在 `build/mingw/results_cmp/`（未提交），
CI 在 benchmark artifact；需要引用数字时按 §1 的命令重跑、从 JSON
现抽，不要从文档抄。

## 1. 本地对照实验：并发强度 × 扫描策略

环境：Windows/MinGW 本地机，NVMe 快盘。固定参数：基表池 32 MB
（≈ 表的 1/8）、LRU、表 200 万行 / 64 KB 页、扫描间隔 1000 ms。
四组：t8 / t16 / t32（线程数递增）与 z11（zipf1.1 + t8）。时长以
"扫描轮数足够"为准（§5）。**z11 组的 theta=1.1 超出 YCSB 适用范围
（theta < 1），该组数据作废**；涉及它的条目（§1.1 后半、§1.5）只保留为
历史线索，不作为证据。

**这批数据只用来说明机制、提出假设，不能作为计时或排序结论**：Windows
与 Linux 在 I/O 路径、调度与计时器上不同，长实验统一放 Linux CI；跨环境
外推不成立。

运行形式（`build/mingw/` 下）：

~~~
mvcc_exp scan_policy=<策略> tp_threads=<N> key_dist=<分布> \
         base_pool_mb=32 replacer=lru duration_s=<秒> --experiment-id=<组名_策略名>
~~~

注意：**defer_chain / defer_paged 未包含在本地组**（本地实验聚焦
bypass 问题），它们的本地行为只能从 CI 报告外推；引用"本地 baseline
最快"时别忘了这个缺口。

### 1.1 TP 吞吐是饱和吞吐

线程数成倍增加，吞吐同量级不动；换成 zipf1.1（热点集中、行冲突率
下降）吞吐显著上升——**后半句来自 theta 越界的 z11 组，已作废**。
仍成立的线索是"吞吐瓶颈在行冲突与共享资源竞争，不在线程供给"；
键分布倾斜是否提高 TPS 待 zipf0.95 的 CI 数据验证。AGENTS.md §11 已按
此收窄。

### 1.2 锁规避维度：只在最高并发档显现

t32（本组最高并发）下 combo 扫描延迟大幅领先 baseline，且 **TP 吞吐
反升**——扫描经池路径的 Fix 次数大幅减少后，池锁竞争下降，TP 的 Fix
不再与扫描排队。锁规避与 I/O 效率是 bypass 的两个正交收益来源，
已写入 AGENTS.md §10。

### 1.3 快盘低并发 = baseline 主场（I/O 维度收益趋零）

t8（TPS 无压力）下 baseline 最快，combo 落后。本地 NVMe 上一次直读
往返很便宜，而冷段直读按 miss 子段成批、散布热行把冷区切碎成大量
短 run，**读调用次数反而多于深度预取的 baseline**——调用粒度退化
是 bypass 在快盘上的真实成本，CI 慢盘上被物理页数的收益盖过。

### 1.4 hotfirst 无主场（策略已移除）

普通 hotfirst 已从系统删除，保留的 hotfirst_bypass 才是热点段策略；
本组数据仅作历史记录。四组全部垫底（延迟最差，多数组 TPS 也最差）。理论收益（先扫常驻页）
被两点抵消：kScan 访问模式下 baseline 顺序扫到热点页时它们同样在
池里（AGENTS.md §10 已记录）；热点段先扫意味着最先撞上 TP 正在
高频更新的页——锁位判定失败率最高的行集中在扫描最前面。

### 1.5 z11：combo 反而最慢（theta 越界，证据作废）

z11 组使用 theta=1.1。YCSB 逆变换要求 theta < 1；theta > 1 时公式不再
对应标准 Zipf 分布，该组只能算无效压力探针，不能作为机制证据。配置已
改为 `zipf0.95`，并用 CI run 11（tp2、bp32、40 s，合法 theta）复测：
combo 与 hotfirst_bypass 在 4 个替换器中的 3 个几乎同值（895 vs 902 ms），
未复现"combo 反而最慢"；clock 下 combo 单点为 1385 ms，但同格 TPS 也从
2521 掉到 1607，属整轮环境干扰，不是策略效应。原假设（多次同步直读与
写回竞争磁盘队列）在本轮不成立；若后续用更小 undo 池/更长时长制造真实
undo I/O 后再观察。候选对策"整段连驻留页一起读"仍属设计变更，须先改
文档再动代码。

### 1.6 t16 combo 的 TPS 反常下降（本地现象，CI 未复现）

中档并发下 combo 扫描延迟领先但 TPS 反降，与最高并发档的方向相反。
CI run 9 在 Linux 上以 8/16/32 三档（4 vCPU runner 上均属超订）复测：
三档 TP 吞吐同量级、策略间无差异，combo 的下降没有出现。判定为 Windows
本地环境/调度噪声，不进入结论；`tp_threads` 因此不固化进默认矩阵
（§2、§6）。

## 2. CI 完整矩阵结论（shared runner，慢盘）

来源：benchmark workflow 多轮汇总报告（6 策略 × 4 替换器 × 池档位）。

- **组合可加性成立**：combo 与 hotfirst_bypass 的基表读几乎逐位
  相同，组合的增量收益全部来自 undo 侧——正是设计预期（基表页访问
  组织 × undo 解析时机正交，AGENTS.md §10）。
- **正反馈环反向兑现**：combo 的 undo 逻辑读比 defer_paged 还低——
  扫描快 → 快照窗口短 → 窗口内提交少 → 走链行少。defer 系解析的
  工作量与扫描时长正相关，这不是独立收益而是乘数。
- **全驻留固定税**：表全驻留（I/O ≈ 0）的池档位下 combo 慢于
  defer_paged——热段快照、哈希驻留判定、双 pass 在无 I/O 可省时
  全是纯开销。bypass 的收益有"必须存在可省的 I/O"这个前提。
- **替换器敏感性减半**：bypass 系策略跨替换器的延迟差异显著小于
  baseline 系——扫描绕开池路径后，替换器行为对扫描的影响被解耦。
- **runner 噪声识别**：个别池档位下出现过全部策略 TPS 同步大幅
  下挫，判定为 runner 干扰并剔除。识别规则已写入 AGENTS.md §12：
  跨策略一致的退化是环境信号，不是策略效应。
- **undo 池档位不进 CI 输入**：192 轮里 up16/up32 两档下策略族层面的
  相对结论一致——小/中池档 bypass 族领先，全驻留档 defer_paged 领先；
  bypass 族内部 combo 与 hotfirst_bypass 的排序会随档位翻转，但幅度
  落在 runner 噪声内，不足以支撑该维度。代码保留 `--undo-pool-mb`
  列表用于复现，CI 默认输入只留基表池档位。
- **并发档不改变策略族排序**：CI run 9（bp32，tp 8/16/32，6×4×3）中
  bypass 族在全部格子占据扫描延迟前两位；TP 吞吐三档同量级且与策略
  无关——饱和吞吐，扫描策略的收益只体现在扫描延迟。该轮 undo 池全程
  驻留（undo 物理读为 0），defer 系的解析差异只剩簿记成本，不足以区分
  两种解析方案。`tp_threads` 保留为可选 CI 输入，不固化进默认矩阵。
- **4 vCPU 上 tp>4 是超订，不是并发压力**：run 9 的 8/16/32 档在 4 vCPU
  runner 上分别为 2×/4×/8× 超订；每线程 TPS 随 1/tp 下降，TP 延迟
  p50/p99 随档位上升。策略族排序在超订档仍稳定，但并发扩展性不能按
  8/16/32 解读；扫描线程本身也占一核，干净的并发对照应用 tp 1/2/3，
  4 与 8 档只作边界/超订参照。
- **干净并发档上 bypass 的 TP 吞吐优势出现，tp4 被 CPU 饱和吃掉**：
  run 10（bp32，tp 1/2/4，6×4×3，40 s，旧 6 策略代码）中 bypass 族在
  全部 12 个格子仍是扫描延迟前二；相对 baseline 的扫描 avg 在 tp1 为
  1.15~1.40×、tp2 为 1.12~1.33×、tp4 为 1.13~1.38×。TP 吞吐在 tp1/tp2
  上 bypass 约 1970/2025、baseline 约 1450/1500（+35%），tp4 两者同为
  ~1550——4 个 TP 线程加扫描线程已占满 4 vCPU，锁规避的吞吐收益消失。
- **tp2 的 defer_paged 块判定为 runner 干扰**：该块 4 个替换器同时出现
  TPS ~900、TP p99 ~34 ms、scan_count 22~27，而同档其他策略正常；
  tp1/tp4 的 defer_paged 无此现象。按"同组配置一致退化是环境信号"剔除，
  不作为策略效应。该轮 undo 池仍全程驻留（undo 物理读为 0），defer 两
  种解析方案的差异依旧不可测。
- **合法高倾斜 zipf0.95 不改变策略族结论**：run 11（tp2、bp32、40 s、5×4）
  中 bypass 族在 lru/arc/lru_k 下占据扫描延迟前二；clock 下 hotfirst_bypass
  仍第一（907 ms），combo 单点 1385 ms 但整轮 TPS 同步掉到 1607，判为环境
  干扰。相对 baseline，bypass 扫描 avg 约 902 vs 1157（1.28×），TP 吞吐
  2521 vs 2015（+25%）；链均跳数 1.35 vs 1.07，冲突率仍为 0，undo 仍全
  驻留。高倾斜的主要效果是提高 TPS、略微加深扫描窗口内的版本链，不改变
  bypass 的领先方向。

## 3. 热行分布核验（scattered 映射）

问题：热行会不会空间聚集，使实验测的是特例？核验方法：zipf0.8、
固定 seed 的全表随机置换，统计页级访问分布。结论：与"页内热点行
密度自然涌现"的散布水平一致，无超比例聚集的头部页，**无空间
聚集**——zipf 的倾斜在行级、通过置换表均匀摊到页级，符合
AGENTS.md §11 的设计意图。seed 固定，此核验可随时重放。

## 4. 代码与测试教训（实现 bypass / 组合策略过程中）

- **测试里 after 快照必须在提交之后取**：`HotFirstBypassSeesCommittedData
  AfterEviction` 首跑失败，原因不是实现而是测试自己在提交前取了
  read_ts——ts ≥ read_ts 按协议不可见（§9.2 判定即走链）。系统是对的，
  测试时序错了。
- **测试不能隐式假设池的驻留状态**：`BypassDeferMainKeepsUndoAndPool
  Untouched` 首跑失败，因为 UpdateRow 本身会把页 Fix 进池（小表 +
  小池恰好全装下），热段快照比测试预期的更大。写池相关断言前先算
  清楚测试自己触发了哪些装载。
- **扫描两种页内行处理共用一个 Impl**（OnRow 参数化）：池路径与
  bypass 路径的行逻辑只有"数据从哪来"不同，复制两份必然漂移。这是
  "优先复用而非重复实现"（§1）在扫描层的落点。
- **结构化编辑后必须读回现场**：一次 Edit 把相邻函数体误删，靠读回
  文件立即发现。批量改动后 grep 函数签名计数是最便宜的回归检查。

## 5. 方法论教训（实验与数据分析）

- **时长下限由扫描轮数决定**：短时试跑在最高并发组只跑得出 1 轮，
  p50 无意义。规则：信 avg/p50 之前先看 `scan_count ≥ 3`。
- **扫描延迟用 avg 不用 p50**：`details` 有逐次 `main_scan_ms` /
  `resolve_ms`，avg = 每次扫描总耗时的均值；p50 在双峰或样本少时与实际
  成本脱节，只作参考。汇总脚本已按 avg 出表，p99 保留作尾部参考。
- **先看 JSON 实际结构再写分析脚本**：字段名靠猜浪费了一轮。
- **凭记忆引用数字不可靠**：本文件初稿曾凭记忆写入数字，重抽全部
  JSON 核对后发现与口述数字有出入（幅度与所属组都有记错的地方）。
  结论必须重新来自数据——这也是本文件只存定性结论的直接原因：
  连刚测完的数字都记不准，隔了几个月更不可能凭文档数字做设计
  依据。
- **长实验只在 CI 上跑**：Windows 本地只做功能冒烟与机制线索；两平台
  的 I/O 路径（无缓冲 I/O 实现）、调度与计时器不同，足以改变策略排序。
  本地跑出的计时数字不用于定矩阵维度，也不跨环境引用。
