# 实验笔记 — 实证结论与分析记录

本文件是研究日志：记录实验观察、数据归因、方法论教训与未定案决策。
它**不是规范**——协议、不变式与契约的唯一权威是 AGENTS.md；两者冲突时
以 AGENTS.md 为准。本文里"待查 / 待验证"标注的条目是未闭合的问题，
不是结论。

数字凡注明来源均可复现：本地数据在 `build/mingw/results_cmp/`（未提交，
可按 §2 命令重跑），CI 数据来自 benchmark workflow 的 artifact。

## 1. 本地对照实验：并发强度 × 扫描策略

环境：Windows/MinGW 本地机，NVMe 快盘。固定参数：基表池 32 MB
（≈ 表 3907 页的 1/8）、LRU、表 200 万行 / 64 KB 页、扫描间隔 1000 ms。
四组：t8 / t16 各 30 s，t32 60 s（10 s 只跑得出 1 轮扫描，p50 无意义，
见 §5 教训），z11 = zipf1.1 + t8 + 30 s。

运行形式（`build/mingw/` 下）：

~~~
mvcc_exp scan_policy=<策略> tp_threads=<N> key_dist=<分布> \
         base_pool_mb=32 replacer=lru duration_s=<秒> --experiment-id=<组名_策略名>
~~~

| 组 | baseline | hotfirst | hotfirst_bypass | bypass_defer_paged |
|---|---|---|---|---|
| t8 | 2328 / 2038 / 31196 | 5346 / 1680 / 22987 | 2720 / 2148 / 34188 | 2990 / 2038 / 909 |
| t16 | 5075 / 2111 / 30974 | 6686 / 1648 / 28331 | 5601 / 2045 / 33252 | 4110 / 1609 / 1043 |
| t32 | 19277 / 1901 / 61179 | 26778 / 1950 / 57798 | 14148 / 2175 / 76824 | **11577 / 2282 / 3991** |
| z11 | 1763 / 3918 / 65315 | 4824 / 2766 / 22297 | 2922 / 4220 / 39371 | 4244 / 3182 / 4839 |

注意：**defer_chain / defer_paged 未包含在本地组**（本地实验聚焦 bypass
问题），它们的本地行为只能从 CI 报告外推；引用"本地 baseline 最快"时
别忘了这个缺口。

### 1.2 TP 吞吐是饱和吞吐（四组共同证据）

t8 / t16 / t32 的 TPS 全部落在 1600–2300 区间，线程数 4 倍不涨吞吐；
TP 循环无限速（`RunTpWorker` 只查 stop 旗标）。z11 的 TPS 3918 ≈ zipf0.8
的两倍——提高吞吐的路径是键分布倾斜（热点集中 → 行冲突率下降），不是
加线程。已写入 AGENTS.md §11：tp_threads 是竞争压力旋钮。

### 1.3 锁规避维度：只在 t32 显现

t32 是 combo 的主场：扫描延迟较 baseline 低 40%（11577 vs 19277 ms），
**TP 吞吐反升 20%**（2282 vs 1901 txn/s），undo 逻辑读少 15×。

归因证据：扫描经池路径的逻辑读（= 总逻辑读 − 冷段直读请求）从 baseline
的 ~7300 次/轮降到 ~800 次/轮（≈ 9×）——扫描不再挤占池锁，TP 的 Fix
不再和扫描的 Fix 排队，TPS 上升顺理成章。锁规避与 I/O 效率是 bypass 的
两个正交收益来源，已写入 AGENTS.md §10。

### 1.4 快盘低并发 = baseline 主场（I/O 维度收益趋零）

t8（TPS 无压力）下 baseline 2328 ms 最快，combo 2990 ms（+28%）。本地
NVMe 上一次直读往返很便宜，冷段直读的读调用次数反而是净支出：combo
每轮 ~920 次读调用 vs baseline ~335 次（预取深度 16 把 3907 页摊成
~245 次 + 逐页 Fix）——直读按 miss 子段成批，散布热行把冷区切碎成
大量短 run，调用粒度退化了。**读调用次数是 bypass 在快盘上的真实成本**，
CI 慢盘上这个成本被物理页数收益盖过。

### 1.5 hotfirst 无主场

四组全部垫底（延迟最差、TPS 除 t32 外也最差）。它的理论收益（先扫
常驻页）被两点抵消：扫描访问模式下 baseline 顺序扫到热点页时它们同样
在池里（AGENTS.md §10 已记录）；而热点段先扫意味着最先撞上 TP 正在
高频更新的页，锁位判定失败率最高的行集中在扫描最前面。

### 1.6 z11：吞吐翻倍 + 链变长 + combo 反而最慢

zipf1.1 下 baseline 延迟反而降到 1763 ms（undo 全驻留时走链是纯内存
操作，链长不是问题），chain_avg_hops 从 1.1 升到 2.6（热行窗口内版本数
上升）。combo 4244 ms，比 baseline 慢 2.4×。待验证假设：TP 写流量
翻倍（undo 写回 + 淘汰）后，combo 每轮 ~880 次同步直读调用与写回
竞争磁盘队列，单次调用延迟放大——即 §1.4 的读调用成本被高写入负载
放大。若成立，直读调用粒度是 combo 在"快盘 + 高写入"区的系统性弱点，
候选对策是"整段连驻留页一起读、读后丢弃"（预取已接受同样的浪费，
§7.5）——属设计变更，须先改文档再动代码。

### 1.7 t16 combo 的 TPS 反常下降（未解释）

t16 下 combo 扫描延迟 −19%（4110 vs 5075）但 TPS 反而 −24%（1609 vs
2111），与 t32 的 +20% 方向相反。介于两者之间的并发度上锁规避收益
与 I/O 开销的平衡点在哪，现有数据说不清。这是 tp_threads 进矩阵（§6
决策 1）的直接动机：需要 CI 复现多档并发强度。

## 2. CI 192 轮结论（shared runner，慢盘）

来源：benchmark workflow `ci_8` 一轮（6 策略 × 4 替换器 × 池档位）的
汇总报告。

- **组合可加性成立**：combo 与 hotfirst_bypass 的基表读几乎逐位相同
  （lru：41244 vs 41187），组合的增量收益全部来自 undo 侧——正是设计
  预期（基表页访问组织 × undo 解析时机正交，AGENTS.md §10）。
- **正反馈环反向兑现**：combo 的 undo 逻辑读 864，比 defer_paged 的
  1962 还低 56%——扫描快 → 快照窗口短 → 窗口内提交少 → 走链行少。
  defer 系解析的工作量与扫描时长正相关，这不是独立收益而是乘数。
- **全驻留固定税**：bp256（表全驻留，I/O ≈ 0）下 combo 比 defer_paged
  慢 ~7%——热段快照、哈希驻留判定、双 pass 在无 I/O 可省时全是纯开销。
  bypass 的收益有"必须存在可省的 I/O"这个前提。
- **替换器敏感性减半**：bypass 系策略跨 4 种替换器的延迟 spread ~20%，
  baseline ~39%——扫描绕开池路径后，替换器行为对扫描的影响被解耦。
- **runner 噪声识别**：bp64/up32 档约 10 个格子出现全部策略 TPS 同步
  −40%，判定为 runner 干扰并剔除。识别规则已写入 AGENTS.md §12：
  跨策略一致的退化是环境信号，不是策略效应。

## 3. 热行分布核验（scattered 映射）

问题：热行会不会空间聚集，使实验测的是特例？核验（zipf0.8、200 万行、
固定 seed 0x5EED5EED 的全表随机置换）：页级访问分布 CV ≈ 1.14，访问量
top 1% 的页只占 ~7.9% 访问——与"页内热点行密度自然涌现"的设计意图
（AGENTS.md §11）一致，**无空间聚集**。zipf 的倾斜在行级、通过置换表
均匀摊到页级。

## 4. 代码与测试教训（实现 bypass / 组合策略过程中）

- **测试里 after 快照必须在提交之后取**：`HotFirstBypassSeesCommittedData
  AfterEviction` 首跑失败，原因不是实现而是测试自己在提交前取了
  read_ts——ts ≥ read_ts 按协议不可见（§9.2 判定即走链）。系统是对的，
  测试时序错了。
- **测试不能隐式假设池的驻留状态**：`BypassDeferMainKeepsUndoAndPool
  Untouched` 首跑失败，因为 UpdateRow 本身会把页 Fix 进池（4 帧恰好装下
  4 页表），热段快照从 {0,1} 变 {1,2,3}。写池相关断言前先算清楚测试
  自己触发了哪些装载。
- **扫描两种页内行处理共用一个 Impl**（OnRow 参数化）：池路径与 bypass
  路径的行逻辑只有"数据从哪来"不同，复制两份必然漂移。这是"优先复用
  而非重复实现"（§1）在扫描层的落点。
- **结构化编辑后必须读回现场**：一次 Edit 把相邻函数体误删，靠读回文件
  立即发现。批量改动后 grep 函数签名计数是最便宜的回归检查。

## 5. 方法论教训（实验与数据分析）

- **时长下限由扫描轮数决定**：t32 10 s 只跑出 1 轮，p50 无意义；改
  30 s（t8/t16/z11）与 60 s（t32）。规则：信 p50 之前先看
  `scan_count ≥ 3`。
- **先看 JSON 实际结构再写分析脚本**：字段名靠猜浪费了一轮。
- **凭记忆引用数字不可靠**：本文件定稿前重抽了全部 16 个 JSON 核对，
  修正了两处记忆偏差（此前口述的"t16/t32 下 combo −40%"实为 t32 −40%、
  t16 −19%；"TPS 恒 2000" 实为 1600–2300 区间且 t16 combo 有反常）。
  写进文档的数字必须重新来自数据。

## 6. 未决决策（登记于 AGENTS.md §14，此处留证据）

1. **tp_threads 进 benchmark 矩阵**：区分度证据 = §1.3 / §1.7（t32
   −40% & TPS +20% vs t16 −19% & TPS −24%，锁规避收益随并发强度放大
   且存在拐点）。代价：6×4 矩阵 ×3 档 = 72 轮，CI 时长重估。
2. **undo 池档位维度砍除**：三轮 CI 均未改变策略间相对结论；undo 侧
   差异在池全驻留时即已显现（本地 undo 物理读恒 0），档位只影响物理读
   绝对值。保留理由仅剩防 undo 池成为隐藏瓶颈（当前最大 undo 文件
   ~8 MB@30 s，远小于 64 MB 档）。
