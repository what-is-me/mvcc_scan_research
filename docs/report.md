# MVCC 持续更新下的全表扫描策略：结论报告

本文是项目的结论层：规范见 [AGENTS.md](../AGENTS.md)，逐轮数据、异常判定与
数据归因见 [experiment_notes.md](experiment_notes.md)。报告只引用具名实验
批次（CI run 编号），不把单一环境的绝对耗时当作可外推的常数。

## 摘要

1. **页面访问组织是第一优先级。** 在“表远大于池”（bp32，表约为池的 8 倍）、
   Linux CI runner 盘（本项目口径的慢盘）、tp1/2（实测）的条件下，
   `hotfirst_bypass` 系的扫描平均耗时约为 baseline 的 1/1.1~1/1.4；TP 吞吐
   在 tp1/tp2 上分别高约 35%（run 10，zipf0.8）与 25%（run 11，zipf0.95）。
2. **收益来自两个正交维度，必须分开归因。** 一是冷段直读减少预取批内对
   已驻留页的重复物理读，代价是读调用数上升；二是扫描绕开池锁，降低与
   TP 的锁竞争。前者取决于盘的瓶颈形态，后者只有在 CPU 尚有余量时才会
   转化为 TP 吞吐。
3. **全驻留是反例。** 表完全驻留时没有可省的 I/O，bypass 的热段快照与
   冷区归并两次额外页表遍历变成纯开销；defer 系整体更快（主扫描不穿插
   undo 访问是候选解释），`defer_paged` 在 run 8 与 run 13 两次同配置重复
   中均领先；run 14 整轮降速（TPS 约 0.58×）但仍第一，领先幅度小。
4. **defer 的页式解析是真实的 CPU/读次数优化，但不是端到端杠杆。** 页式把
   undo 逻辑读减少约 15 倍、解析段耗时降低约 2.5 倍；但在当前负载下解析段
   只占端到端耗时的 0.02% 以下，链式与页式的总延迟差异不可见。
5. **并发档位的解释必须扣除扫描线程。** 4 vCPU runner 上，扫描线程本身占
   一核；tp1/2 是实测的干净并发档，tp3 恰在边界（未实测，不能假定收益
   保留），tp4 在扫描期间已构成 5 个可运行线程。
6. **普通 hotfirst 已移除。** 在 kScan 访问模式下它不减少物理读，反而最先
   撞上 TP 正在更新的热点行；保留的 `hotfirst_bypass` 才承担“先扫常驻页”
   的语义。
7. **替换策略不是主变量。** baseline 系下 Clock 多次出现扫描延迟最差；
   bypass 系跨替换器差异明显收窄，ARC/LRU/LRU-K 之间没有稳定赢家。

## 1. 研究问题与系统模型

系统研究：行存数据库采用 MVCC、持续存在 inplace 更新事务时，全表扫描应
如何组织页面访问与版本解析。原型只做扫描与更新，不做 insert/delete、
WAL、undo GC 或索引；表在初始化后行数恒定，undo 只追加。

扫描策略共 5 种：

| 策略 | 页面访问 | 版本解析 |
|---|---|---|
| baseline | 按页号升序扫全部基表页 | 立即走链 |
| hotfirst_bypass | 热点段（扫描开始瞬间驻留的页）走池，冷段查池直读文件 | 立即走链 |
| bypass_defer_paged | 同 hotfirst_bypass 的页面访问 | 记录链头，主扫描后按 undo 页分桶批量解析 |
| defer_chain | 按页号升序扫 | 记录链头，主扫描后逐条沿链回溯 |
| defer_paged | 按页号升序扫 | 记录链头，主扫描后按 undo 页分桶批量解析 |

替换策略 4 种：LRU、Clock、ARC、LRU-K。undo 池用 LRU；基表池可用任意一种。

评价指标以 `details[]` 的逐次扫描平均值为准（`avg = main_scan_ms +
resolve_ms` 的均值），p99 只作尾部参考。p50 不作为主指标：扫描耗时可能
双峰，p50 与实际成本脱节。

## 3. 机制与因果

### 3.1 页面访问组织：bypass 的收益与前提

`hotfirst_bypass` 在扫描开始瞬间固化热点集合，热点段走池，冷段在池锁内
一次判定未驻留页，再整段直读文件（§7.2 O1）。与 baseline 相比，它省掉
两件事：

- **逐页 Fix 的簿记与池锁**：冷段不再为每一页做 Fix/Unpin、淘汰与页表
  操作；
- **扫描对池的驻留占用**：冷页不进池，不会把 TP 的热点页挤出去。

收益的两个来源必须分开看：

- **I/O 效率**：冷段整段直读省掉预取批内对已驻留页的重复读，物理读页数
  下降（run 10 tp1 中位约 −20%）；代价是散布的热行把冷段切碎，读调用数
  反而上升（约 2.4×）。净收益取决于盘的瓶颈形态：每页传输主导时页数下降
  占优；每次调用固定延迟主导（如 HDD 寻道/队列）时，调用数上升可能是
  负债。本项目的 CI runner 从结果看更接近前者——是慢盘，但瓶颈更可能在
  页传输，而非每次调用的固定延迟。
- **锁规避**：扫描经池路径的逻辑读大幅减少，池锁竞争下降；只有在 CPU
  尚有余量时，这部分才会转化为 TP 吞吐。run 10 的 tp1/tp2 上 bypass 的
  TP 吞吐比 baseline 高约 35%；tp4 时 4 个 TP 线程加扫描线程已占满
  4 vCPU，吞吐差异消失，只剩扫描延迟收益。tp3 未进批次，处在边界，
  收益能否保留取决于扫描线程的 I/O 等待是否让出 CPU，未验证。

因此“bypass 一定更快”不成立。它的成立条件是：表明显大于池、存在可省的
I/O 或池锁竞争、且 CPU 没有被扫描与 TP 同时打满。

普通 `hotfirst` 不满足这个条件：kScan 模式下 baseline 顺序扫到热点页时
它们通常还在池里，先扫并不减少物理读；热点段又最先撞上 TP 正在高频更新
的行，锁位判定失败率最高。普通 hotfirst 已从系统移除，历史数据只作记录。

### 3.2 并发档位：扫描线程也要占一核

CI 标准 runner 只有 4 vCPU。扫描线程本身是可运行线程，因此：

- tp1/2 是实测的干净并发档（扫描期间总线程数 ≤ 3）；
- tp3 在扫描期间恰为 4 个可运行线程，是边界档，未实测；
- tp4 在扫描期间构成 5 个可运行线程，是轻度超订；
- tp8/16/32 是 2×/4×/8× 超订，只能作调度开销的边界参照。

run 9 的 8/16/32 档每线程 TPS 随 1/tp 下降、TP 延迟 p50/p99 随档位上升，
聚合吞吐不变；run 10 的 tp1/2 则显示 bypass 的 TP 吞吐优势，tp4 因 CPU
饱和消失。两个批次合起来说明：**tp_threads 是竞争压力旋钮，不是吞吐供给
旋钮；并发档位必须按“总可运行线程数”解释，而不是只看 TP 线程数。**

### 3.3 defer 与 undo 解析：页式优化在哪里生效

defer 把“走链”推迟到主扫描之后：主扫描只记录重读后的链头，解析阶段再
访问 undo 页。页式解析把待解析的 undo_row_id 按 undo 页号分桶，逐桶加载
并在页内批量解析，同页的 prev 就地续跳。

run 12 在 up16、120 s、zipf0.95、tp2 下测到：

- undo 文件增长到 9~20 MB，说明脏页确实被淘汰写回；
- 但 `undo_physical_reads = 0`、undo 命中率 1.000：扫描需要的 undo 活跃
  窗口约为“扫描时长 × 更新速率”（量级不足 1 MB），远小于 16 MB 池，
  被淘汰的旧页不会再被读回；
- `defer_paged` 的 resolve 约 0.07~0.12 ms/次，`defer_chain` 约
  0.18~0.28 ms/次（约 2.5 倍）；undo 逻辑读每轮约 0.76 万 vs 11.5 万
  （约 15 倍）；
- 但相对约 1.2 s 的主扫描，解析段节省不足 0.02%，端到端不可见。

结论：**页式解析的收益是减少 undo 页重复加载的 CPU/读次数优化，不是当前
负载下的端到端优化。** 它要兑现，需要“undo 活跃窗口 > undo 池”或链工作量
大幅上升；当前参数下链式与页式都只需保留，不据此排序。

`bypass_defer_paged` 的解析段更小（约 0.05 ms/次），因为 bypass 主扫描
记录的行数更少；但它相对 `hotfirst_bypass` 没有稳定收益，反而多一段解析
开销。两者在 run 10/11 的中位差异落在噪声内；在表全驻留时，组合策略的
固定开销更明显。

### 3.4 替换策略：bypass 会削弱替换器的影响

- **baseline 系**：Clock 多次出现扫描延迟最差。run 9 的 bp32 档、run 10 的
  tp1 档、run 12 与 run 18 的 tp2 档都能看到 Clock 的 baseline 扫描慢于
  LRU；机制上 Clock 只给“第二次机会”，对全表顺序扫描的冷页保护弱于 LRU。
- **bypass 系**：冷段直读绕开池，替换器对扫描的影响被解耦；跨替换器的
  扫描延迟差异明显收窄。ARC/LRU/LRU-K 之间没有稳定赢家。run 11 的
  clock/combo 与 run 12 的 clock/hotfirst_bypass 单点已由 run 15 与
  run 17/18 重复排除，clock 格回到其他替换器水平（约 1.00×）；其他单格
  异常（如 lru_k/defer_paged）仍按环境信号剔除。
- **全驻留**：替换器差异进一步缩小；run 8/13/14 的全驻留档均由
  `defer_paged` 领先，而不是任何 bypass 策略。

实践含义：默认选 LRU 即可；如果必须用 baseline 系并且扫描占比高，避免
Clock；ARC/LRU-K 的额外复杂度在当前负载下没有稳定回报。

## 4. 条件性结论

| 条件 | 推荐 | 原因 |
|---|---|---|
| 表远大于池（bp32，表/池约 8×），Linux CI runner 盘（本项目口径的慢盘），tp1/2（tp3 未实测） | `hotfirst_bypass` | 扫描 avg 的 baseline/bypass 比值约 1.1~1.4（run 10/11/12）；TP 吞吐 tp1/tp2 +35%（run 10，zipf0.8）、tp2 +25%（run 11，zipf0.95） |
| 同上，但需要两阶段可观测 | `hotfirst_bypass` 或 `bypass_defer_paged` | 两者扫描延迟中位差异在噪声内；组合策略多一段解析开销 |
| 表全驻留（bp256，run 8/13/14） | `defer_paged` | 没有可省的 I/O；bypass 的热段快照与冷区归并两次额外页表遍历是纯开销。数据上 defer 系整体快于 baseline，主扫描不穿插 undo 访问是候选解释；run 8/13 两次同配置重复均领先，run 14 整轮降速但仍第一，领先幅度约 5~10 ms，归因未完全拆开（§6 第 1 项） |
| 慢盘，且慢在每页传输而非每次调用固定延迟 | bypass 系 | 物理页数约 −20%、读调用约 2.4×（run 10 tp1）；传输主导时净收益为正，HDD 类调用延迟主导时可能为负 |
| 4 vCPU，tp4+ | bypass 系（仅扫描延迟） | TP 吞吐优势被 CPU 饱和吃掉；扫描延迟优势仍在 |
| undo 活跃窗口远小于池（当前原型） | 任意；defer 两种解析等价 | 解析段 <0.02% 端到端；页式只减少逻辑读/CPU |
| undo 活跃窗口 > 池，或链工作量大幅上升 | 优先 `defer_paged` | 页式减少 undo 页重复加载；需先制造读 miss 再验证 |
| baseline 系 + 扫描占比高 | 避免 Clock | Clock 的扫描延迟多次垫底 |
| 需要稳定、可解释的默认配置 | LRU | ARC/LRU-K 无稳定优势，Clock 有反例 |

## 5. 有效性边界与反例

- **全驻留反例**：run 8 的 bp256 单轮矩阵中表基本全驻留，`defer_paged` 与
  `defer_chain` 都快于 baseline，bypass 族的固定开销暴露。run 13 同配置
  重复复现了 `defer_paged` 第一；run 14 整轮降速（所有策略扫描约 2×、
  TPS 约 0.58×）但排序仍以 `defer_paged` 第一，按环境信号剔除幅度比较。
  任何“bypass 总是更快”的结论都越过了这条边界。
- **快盘 + 低并发**：物理页数下降的收益变小，而读调用数上升的固定开销
  占比变大；笔记 §1.3 的本地线索是 baseline 主场。本报告不把 CI 的排序
  外推到更快的本地 NVMe。
- **CPU 饱和**：tp4+ 或扫描与 TP 同时占满核心时，锁规避的 TP 吞吐收益
  消失；只剩扫描延迟。
- **高倾斜的合法上界**：`zipf0.95` 是 YCSB 逆变换的允许区间上界；
  `zipf1.1` 越界，相关历史数据已作废，不能作为机制证据。
- **无 insert/delete、无 GC、无 WAL**：结论不覆盖有空洞、有回收、有崩溃
  恢复的系统；undo 只追加使版本链只增长不缩短。
- **整块退化与单格异常要分开**：run 10 的 tp2/defer_paged 是 4 个替换器
  整块一致退化（TPS 与扫描同时下降），run 14 的全驻留重复是整轮降速
  （所有策略扫描约 2×、TPS 约 0.58×），都按“同组一致退化=环境信号”
  确定性剔除幅度比较。run 11 的 clock/combo 与 run 12 的
  clock/hotfirst_bypass 已用 run 15 与 run 17/18 同配置重复，clock 格
  回到其他替换器水平（约 1.00×），归为单轮环境干扰；lru_k/defer_paged
  等其他单格异常仍按环境信号剔除。报告采用跨替换器中位；单格排序不据此
  下结论。
- **并发 benchmark run 会互相干扰**：run 17/18 同时派发时，末尾
  `defer_paged` 主扫描约为 `defer_chain` 的 1.5×，同格 TPS/p99 同步恶化；
  单独重复 run 19 回到 1.06×，强异常未复现，残余差异在轮间波动内。计时
  实验应串行派发，不把并发 run 的末尾格子当策略证据。
- **Windows 本地数据**：仅用于功能冒烟，不用于计时与策略排序。

## 6. 未解释现象与后续工作

1. **全驻留下 defer_paged 的领先来源**：run 8 与 run 13 两次同配置重复
   均以 `defer_paged` 第一，run 14 整轮降速但仍第一，稳定性已确认；尚未
   拆开的是领先的 5~10 ms 来自 defer 的解析时机、扫描顺序还是替换器
   交互，需要插桩或增加对照。
2. **TPS 饱和的瓶颈分解**：当前只观察到聚合吞吐饱和，未拆分池锁等待、
   行锁冲突、磁盘队列与 CPU 调度各自的占比；“锁规避维度”的强弱因此只能
   按 tp 档位间接判断。
3. **undo 活跃窗口 > 池的场景**：run 12 只制造了写回，没有制造读 miss；
   要验证页式的 I/O 收益，需要更小的 undo 池、更高的更新速率或更长的
   扫描窗口。这属于参数实验，不改代码；若需要突破当前 16 MB 下限，先改
   AGENTS 的取值范围再动实现。
4. **跨平台**：Linux CI 的 O_DIRECT 行为与 Windows 的 NO_BUFFERING 不完全
   相同；计时结论不跨平台外推。
